# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

PsychBeacon 24/7 is a custom, high-performance remote desktop tool for using a macOS client to control a remote Windows host — ultra-low-latency, high-refresh-rate (120Hz+) streaming, seamless virtual multi-display management, and shared rich clipboard history, replicating premium Parsec/Moonlight features without a subscription.

This repo is very early-stage, but **the full chain works end-to-end as of 2026-09-26**: macOS client discovers the Windows host (LAN or Tailscale mesh), requests a stream, the host adds a virtual display and starts capturing/NVENC-encoding to that client, and the client receives, decodes, and renders it in a window showing the real remote desktop — confirmed over an actual Tailscale/WireGuard connection between two machines on different physical subnets, not a same-host simulation. The input half of the sidecar (keyboard/mouse) is now built on both sides — Windows-side verified against real `SendInput`/cursor movement, Mac-side unverified (see module 4). Multi-display window orchestration is also built (host can add N displays per session, client stands up N independent windows) but unverified against more than one real display. Still unbuilt: clipboard sync.

## Repository layout

Two independent components, each with its own toolchain — there is no shared build system or workspace tying them together:

- `windows-host/` — Rust crate; runs on the Windows machine being controlled.
- `mac-client/` — Swift package; runs on the macOS client. **Requires macOS/Xcode to build** — it cannot be built or type-checked from this Windows checkout.

## Commands

**windows-host** (Rust, from `windows-host/`):
```
cargo check          # type-check
cargo run             # build and run the launcher
cargo build --release
```
No test suite exists yet. **Run elevated (Administrator)** once the real
driver is installed — the VDD registry write and device open both need it;
without elevation they fail with a logged warning and the launcher keeps
running in a degraded mode (discovery still works). See
[`windows-host/docs/vdd-setup.md`](windows-host/docs/vdd-setup.md).

**mac-client** (Swift, from `mac-client/`, on macOS only):
```
swift build
swift run
```
Verified building and running on real hardware (macOS, Swift 5.9 toolchain, this repo's macOS 13+ target) as of 2026-09-26, including the full network path — see module 4 below. Set `PSYBEACON_TARGET_HOST=<tailscale-hostname>` if connecting over Tailscale to a multi-device tailnet (the default "psybeacon" substring only matches a host actually named that).

## Architecture

Four modules, in the order data flows through them at connection time:

1. **Network discovery & routing** (`mac-client/Sources/PsychBeaconClient/NetworkDiscovery.swift`, answered by `windows-host/src/main.rs`) — *implemented; actually called for the first time 2026-09-25* (`AppDelegate.connectToHost` — before that, module 4 always used the file-based test harness, so this code compiled but its runtime behavior was unverified). On launch, the client sends a UDP broadcast (`PSYBEACON_DISCOVER_V1` on port 43701) via a raw BSD socket (Network.framework doesn't expose `SO_BROADCAST`, so it can't reliably send to a broadcast address). If the host answers, the client uses the reply packet's *source address* as the host IP — the reply payload is just an identifying token, not the IP — and connects directly (LAN path, lowest latency). If nothing answers within the timeout, the client shells out to the local `tailscale` CLI (`status --json`) to find the host's 100.x.x.x mesh IP and routes over the Tailscale/WireGuard tunnel instead. This module hands later modules an opaque `HostRoute` (`.lan` or `.tailscale`) carrying the host's address and the discovery port — module 4 reuses that same port as the control channel for the start-stream request (see module 3).

2. **Windows host controller & virtual display driver** (`windows-host/src/vdd.rs`) — *implemented and verified end-to-end against real driver v0.45.0.0 on 2026-09-22* (registry write → device open → add-display → heartbeat → version query, all confirmed working elevated). Not bundling the driver itself. This is a Rust port of [nomi-san/parsec-vdd](https://github.com/nomi-san/parsec-vdd)'s `core/parsec-vdd.h` (verified against the real header + its reverse-engineered docs, not assumed from the original spec — two corrections came out of that):
   - `write_custom_resolutions` writes up to 5 `(width, height, hz)` presets to `HKLM\SOFTWARE\Parsec\vdd\<slot>` (REG_DWORD `w`/`h`/`hz`) — this registry mechanism is real, but must run *before* the device is opened; the driver only reads it at adapter init, not per-display.
   - `VddSession::start` opens the device (`VDD_ADAPTER_GUID`, resolved via SetupAPI — there's no fixed symbolic link path), adds a display via IOCTL, and spawns a heartbeat thread pinging every **50ms**. The original spec's "1-second heartbeat" had it backwards: 1 second is the driver's watchdog *timeout* — if pings stop for ~1s the driver unplugs every virtual display, so the actual requirement (per upstream docs) is pings every ~100ms or tighter.
   - `VddSession` removes the display and closes the handle on `Drop`, which is what stands in for "clean up on client disconnect" until module 3 exists to actually own a per-client connection and drop the session when it ends.
   - The driver binary itself (`mm.inf`/`mm.dll`/`mm.cat`) is proprietary (built and signed by Parsec, not part of the MIT-licensed wrapper this was ported from) and is **not vendored here** — installing it is a manual prerequisite, see [`windows-host/docs/vdd-setup.md`](windows-host/docs/vdd-setup.md). Without it, `main.rs` logs a warning and keeps running in a degraded mode rather than failing outright.

3. **Capture, video streaming, and the client-request protocol** (`windows-host/src/capture.rs`, `encode.rs`, `main.rs`) — *verified end-to-end 2026-09-25, simulating the client side*: a client sends `PSYBEACON_START_STREAM_V1:<basePort>:<count>` to the host's discovery socket (same port as module 1's ping, a new message type — `run_discovery_responder` in `main.rs` dispatches on content, not a separate listener) after resolving a `HostRoute`; the host learns the client's IP from the packet's source (same non-spoofable pattern as discovery) and spawns `run_multi_stream_session` on a background thread: add `count` displays sequentially (each needs its own settle delay — see the ACCESS_LOST note below), reply with a `PSYBEACON_STREAM_INFO_V1:<json>` manifest (per-display stream/sidecar ports and real bounds, since the driver — not the host code — decides where an added display lands), then run one capture → NVENC-encode → raw H.264-over-`udp://<client>:<port>` loop per display concurrently (`run_display_stream`, one thread each) until `shutdown` fires. v1 scope: one *client session* at a time (a request while one's active is logged and ignored, not queued) but that session can cover multiple displays. No VddSession at launch anymore — each display is fully self-contained, added on request and removed (via `Drop`) when its stream ends.
   - `capture.rs`: DXGI Desktop Duplication, scoped to specifically the display this process just added (a before/after snapshot diff — see `for_new_output`'s doc comment — not name-matching, since the adapter is shared with whatever else is using it, e.g. a live Parsec session). Not zero-copy — does a GPU→CPU readback (`CopyResource` to a staging texture, then `Map`) so frames can go over a pipe to FFmpeg; true zero-copy would need direct NVENC SDK integration or an in-process `AVHWFramesContext`.
   - `encode.rs`: spawns `ffmpeg` as a subprocess, feeds it raw BGRA frames over stdin, NVENC-encodes to a local file or a `udp://`/`srt://` URL — **always raw elementary H.264, not MPEG-TS** (changed 2026-09-25 so mac-client can parse NAL units directly rather than demux a container — see `NALUnitParser.swift`). Verified against real hardware (RTX 4080) with a synthetic test pattern, actual captured bytes, and over a real UDP socket end-to-end through the full request protocol above. The original spec's `preset=ultrafast`/`tune=zerolatency` are x264 flag *names* that don't exist for `h264_nvenc` — real equivalents (verified via `ffmpeg -h encoder=h264_nvenc` on this machine, not assumed) are `-preset p1`, `-tune ull`, plus a distinct `-zerolatency 1` boolean. Also: this machine's first FFmpeg install (Gyan 9.0.2) was compiled against a newer NVENC SDK than the installed driver supports and failed outright — fixed by installing an older build (BtbN 7.1.5) rather than touching the GPU driver.
   - Fixed 2026-09-25, previously the long-standing blocker: `VddSession::start` (`vdd.rs`) now sleeps 2s after adding the display before returning. Root cause, found via `--diagnose-capture`/`--diagnose-settle`: calling `DuplicateOutput` on a display too soon after `VddAddDisplay` wedges it into a state that recreating the duplication interface *afterward* does not recover from (measured minimum working delay: 1s; earlier theories — topology attachment, elevation, a DWM-level abandoned lock — were each tested and ruled out first). Full investigation in `capture.rs`'s module doc comment.
   - Known gap, found force-killing test processes: Windows doesn't kill a process's children when the parent is force-killed, so a force-killed launcher leaves its `ffmpeg` encoder subprocess running indefinitely — see `encode.rs`'s doc comment. Only bites ad hoc force-killed test sessions; every real shutdown path is graceful.
   - `main.rs --stream-test SECONDS [OUTPUT]` runs the whole pipeline standalone; `--network-test SECONDS OUTPUT_URL [SOURCE_BGRA_FILE]` exercises just encode+network from a static frame; `--diagnose-capture` / `--diagnose-settle SECONDS` are the read-only tools that root-caused the settle-delay fix; `--remove-index N` removes a specific stray display directly. All exit cleanly on their own (no Ctrl+C needed) — prefer these over ad hoc testing that needs an external Ctrl+C or force-kill; see `vdd.rs`'s incident notes for what killing a process mid-session cleanup cost last time.
   - `sidecar.rs` — *verified end-to-end 2026-09-26* against real `SendInput`/`SetCursorPos`, via a simulated PowerShell WebSocket client (confirmed cursor moved to the exact expected pixel for a `mouseMove` on a non-origin display). A WebSocket server (`tungstenite`, one connection at a time per port — same v1 scope as the video path), started as a background thread per display in `run_display_stream` and stopped/joined before that function returns (so the port is free for a later session). Port is `SIDECAR_PORT + display index` (base `43703`) since multi-display sessions run one sidecar server per display concurrently — see module 4's manifest below. Receives JSON input events (`mouseMove`/`mouseDown`/`mouseUp`/`scroll`/`keyDown`/`keyUp`) and injects them via `SendInput`/`SetCursorPos`; normalized `(x, y)` in `[0, 1]` are mapped onto the specific display's `DesktopCoordinates` bounds (`capture.rs`'s `DesktopDuplicator::bounds()`), not the whole virtual desktop, so a click at the client's origin lands on that display's corner regardless of its position on a multi-monitor host.

4. **macOS client & sidecar portal** (`mac-client/Sources/PsychBeaconClient/`) — *verified end-to-end 2026-09-26, over a real Tailscale connection between two machines on different physical subnets — not localhost, not a simulation.* The full chain confirmed working in one run: discovery → Tailscale fallback → start-stream request → host adds display/captures/encodes → raw H.264 over the real WireGuard tunnel → NAL reassembly → VideoToolbox decode → Metal render → window shows the actual remote desktop.
   - `VideoDecoder.swift`/`MetalRenderer.swift`: `VTDecompressionSession` wrapper + Metal renderer sampling decoded NV12 frames as separate Y/CbCr textures (YCbCr→RGB in the fragment shader).
   - `NALUnitParser.swift`: reassembles Annex-B NAL units from the raw byte stream `encode.rs` sends, builds a `CMFormatDescription` from the stream's SPS/PPS (`CMVideoFormatDescriptionCreateFromH264ParameterSets`), and wraps frame NALs into AVCC-framed `CMSampleBuffer`s for `VideoDecoder`. Assumes in-order, lossless delivery — UDP guarantees neither, and SPS/PPS are only sent once, at stream start, so a lost early packet corrupts the whole session until reconnect. Documented as a known gap, not fixed; see that file's doc comment for what a real fix needs (sequence numbers, periodic repeated parameter sets, or SRT).
   - `NetworkStreamReceiver.swift`: sends the start-stream request (module 3) and receives the response on a raw BSD UDP socket — matching `NetworkDiscovery.swift`'s style deliberately, rather than introducing Network.framework as a second networking approach.
   - `AppDelegate.connectToHost` is the real path (module 1 discovery → module 3 request → decode → render); `AppDelegate.playTestFile` (pass a file path as the first CLI argument) is kept as a regression-test harness for decode/render in isolation from the network.
   - Getting this actually connecting surfaced two real bugs, both fixed — see `NetworkDiscovery.swift`'s doc comment: (1) `tailscale status --json` reports `"Peer": null`, not an empty object, when the tailnet has no other devices — a plain `decode` treated that as a hard error; (2) the Tailscale target was a hardcoded "psybeacon" substring that could never match a real machine's actual hostname on a multi-device tailnet — now `PSYBEACON_TARGET_HOST`-configurable. Also: `DiscoveryError.tailscaleUnavailable` used to cover two different failure modes (CLI not found vs. found-but-no-matching-peer) with one identical message, which made a live debugging session undiagnosable ("same error" after a real fix gave no signal) — split into distinct, specific cases.
   - LAN discovery correctly returned nothing during this same debugging session because the two machines were on different physical subnets (`192.168.10.x` vs `192.168.1.x`) — broadcast doesn't cross subnets. That's expected behavior, not a bug; don't "fix" it by trying to make broadcast cross subnets.
   - `InputSidecar.swift`/`InputCaptureView.swift`/`KeycodeMap.swift` — sidecar input, Mac side, **written 2026-09-26, unverified (no macOS toolchain here)**. `InputSidecar` is a thin `URLSessionWebSocketTask` client (native, no dependency) connecting to `ws://<host>:<sidecarPort>` and sending the exact JSON schema `sidecar.rs` already parses. `InputCaptureView` (an `MTKView` subclass, one per display window — see below) overrides the standard `NSResponder` mouse/keyboard methods, normalizes mouse coordinates to `[0, 1]` against its own bounds (flipping y — AppKit is bottom-left, the host expects top-left), and forwards through its window's own `InputSidecar`. `KeycodeMap` translates `NSEvent.keyCode` (Carbon-era, non-alphabetical scancodes) to Windows VK codes for a deliberately partial set (letters, digits, common editing/nav keys, modifiers, F1–F12) — extend it if a missing key matters in practice rather than guessing entries that can't be verified from this machine.
   - `DisplayNegotiator.swift`/`DisplayWindowController.swift` — multi-display window orchestration, **written 2026-09-26, unverified against more than one real display**. `DisplayNegotiator` sends `PSYBEACON_START_STREAM_V1:<basePort>:<count>` and waits on the same socket (mirroring `NetworkDiscovery`'s send-then-recv-on-one-fd pattern, wrapped in `withCheckedThrowingContinuation` the same way) for the host's `PSYBEACON_STREAM_INFO_V1:<json>` manifest, decoded into `[DisplayInfo]` — one entry per display actually added, since the host may add fewer than requested if a display fails partway through. `AppDelegate.connectToHost` then creates one `DisplayWindowController` per manifest entry: each owns its own window, `InputCaptureView`, `VideoDecoder`/`MetalRenderer`, `NetworkStreamReceiver` (bound to that display's `streamPort`), and `InputSidecar` (connected to that display's `sidecarPort`) — fully independent pipelines, not one window/decoder juggling multiple streams. Display count is `PSYBEACON_DISPLAY_COUNT` (default 1, so the already-verified single-display path is unchanged when unset). The file-based test harness (`playTestFile`) is untouched by this and still uses one ad hoc window, since it has no manifest to negotiate.
   - Still unbuilt: clipboard sync (NSPasteboard ↔ Win32 clipboard) and telling the host to stop streaming when the client disconnects (right now each stream just keeps running server-side until the host process itself is stopped).
   - This is the one module built without any compiler feedback during writing — no macOS toolchain in the environment it was written in. Every file compiled clean on the first `swift build` each time, including the CMSampleBuffer/CoreVideo/raw-socket code, which had no prior verification at all. See `AppDelegate.swift`'s doc comment for the one build-environment gotcha found: `NSApplication`-based apps need an actual interactive WindowServer session, so running via an automation/agent context (as opposed to a real Terminal window) launches and hangs completely silently, no crash or output at all.

## Conventions established so far

- Protocol constants (port `43701`, the `PSYBEACON_DISCOVER_V1`/`PSYBEACON_HOST_V1:`/`PSYBEACON_START_STREAM_V1:` tokens) are duplicated by hand across `NetworkDiscovery.swift`, `NetworkStreamReceiver.swift`, and `windows-host/src/main.rs`. If they diverge, the relevant exchange silently stops working — there's no shared schema file yet, so keep them in sync by hand until one exists.
- `windows-host` TODOs are marked `// TODO(module N): ...` pointing at the module in this file that will fill them in — grep for `TODO(module` before adding new host functionality to see what's already flagged.
- `vdd.rs` is a deliberately faithful port of upstream's C header/docs (constants, IOCTL codes, function shapes match 1:1) rather than a redesign — if the driver's behavior seems off, diff against the upstream source linked in that file's doc comment before assuming the port is wrong. **"Faithful" means matching upstream's actual choices, not substituting equivalent-looking ones** — the access-rights bug below happened because `FILE_GENERIC_READ | FILE_GENERIC_WRITE` looked like a reasonable stand-in for upstream's plain `GENERIC_READ | GENERIC_WRITE` and wasn't. The known deviations from the original PsychBeacon spec text (heartbeat cadence; the registry step is real but lives in the README's "Known Limitations" section rather than the core API docs) plus two real bugs found getting this working against actual hardware (wrong `CreateFileW` access rights; an `HRESULT`-vs-`WIN32_ERROR` comparison that silently masked the first bug's real error) are called out in `vdd.rs`'s module doc comment — treat that comment, not the original spec prose, as authoritative for module 2.
