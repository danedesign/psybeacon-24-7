# Timeline

A running log of what's been solved (**Troubleshooting**) and what's been added (**Update**), in chronological order. Update this whenever a milestone lands — a verified feature, a resolved bug, a new module started.

Built from git history plus this repo's session notes (CLAUDE.md and prior Claude Code conversations). Codex's own chat history on the Mac client side isn't visible from here, so anything decided/fixed purely in that session and not reflected in a commit or CLAUDE.md may be missing.

| Date | Type | Title | Description |
|---|---|---|---|
| 2026-09-22 | Update | VDD driver integration verified | Registry write → device open → add-display → heartbeat → version query all confirmed working, elevated, against real driver v0.45.0.0. |
| 2026-09-22 | Troubleshooting | VDD access-rights bug | `FILE_GENERIC_READ \| FILE_GENERIC_WRITE` looked like a valid stand-in for upstream's `GENERIC_READ \| GENERIC_WRITE` but wasn't — driver rejected the expanded form. |
| 2026-09-22 | Troubleshooting | HRESULT vs WIN32_ERROR comparison bug | Comparing an `HRESULT`'s raw code against a `WIN32_ERROR` constant never matched, silently masking the access-rights bug's real error. |
| 2026-09-25 | Update | Initial commit — modules 1–2 done, module 3 half-verified | Network discovery, VDD control, and capture+encode (independently) landed. |
| 2026-09-25 | Troubleshooting | ACCESS_LOST bug root-caused and fixed | Three false theories (topology, elevation, DWM lock) ruled out before finding the real cause: `DuplicateOutput` called too soon after `VddAddDisplay`. Fixed with a settle delay in `VddSession::start`. |
| 2026-09-25 | Troubleshooting | FFmpeg/NVENC SDK version mismatch | Gyan 9.0.2 build required a newer NVENC SDK than the installed driver exposed. Fixed by switching to BtbN 7.1.5 rather than touching the GPU driver. |
| 2026-09-25 | Update | Module 4 started — VideoToolbox decode + Metal render | Written without a macOS toolchain available at the time. |
| 2026-09-25 | Update | Module 4 first slice verified | Decode/render confirmed correct (colors, motion, test-pattern counter) on real macOS hardware. |
| 2026-09-25 | Update | Network receive path wired | Client-request protocol (`PSYBEACON_START_STREAM_V1`) plus the Mac-side receiver, connecting modules 1/3/4 together. |
| 2026-09-25 | Troubleshooting | Wrong virtual display removed | A force-killed test process left an orphaned display; a wrong guess at which index was safe to remove took out the user's live Parsec session instead. Lesson: never force-kill a process owning a `VddSession` — use the self-terminating `--stream-test`/`--diagnose-*` flags. |
| 2026-09-26 | Troubleshooting | Tailscale `"Peer": null` crash | `tailscale status --json` reports `null`, not `{}`, when the tailnet has no peers; a plain decode treated that as fatal. |
| 2026-09-26 | Update | Tailscale target host made configurable | Hardcoded "psybeacon" hostname substring replaced with `PSYBEACON_TARGET_HOST` env var, needed for a real multi-device tailnet. |
| 2026-09-26 | Troubleshooting | Undiagnosable Tailscale error split into two cases | One generic `tailscaleUnavailable` covered both "CLI not found" and "no matching peer" with the same message; split so retries are actually diagnosable. |
| 2026-09-26 | Troubleshooting | LAN discovery "failure" explained | Host and Mac were on genuinely different physical subnets — broadcast doesn't cross subnets. Confirmed expected behavior, not a bug. |
| 2026-09-26 | Update | Windows Firewall rule added for discovery | Inbound UDP allow rule for port 43701 — a real gap since earlier testing only used loopback. |
| 2026-09-26 | Update | **Milestone: full pipeline verified end-to-end** | Discovery → Tailscale fallback → stream request → capture/encode → NAL reassembly → decode → render, over a real Tailscale/WireGuard link between two machines on different subnets. Remote desktop visibly rendered in the client window. |
| 2026-09-26 | Update | Sidecar input channel added | WebSocket keyboard/mouse forwarding. Windows side (`sidecar.rs`) verified against real `SendInput`/`SetCursorPos`, including exact coordinate mapping onto a non-origin display. Mac side written but unverified (no macOS toolchain in this session). |
| 2026-09-26 | Update | Multi-display window orchestration added | Host can add N virtual displays per session and replies with a manifest (per-display ports + bounds); client stands up one independent window/decoder/renderer/input-sidecar per display. Unverified beyond `count=1` — no hardware test with multiple displays yet. |
| 2026-09-26 | Update | `swift build` verified clean on the sidecar + multi-display code | Codex on the Mac pulled `bf40430` and built successfully — one pre-existing Swift 6 async-context warning (`NSApp.activate`), no errors. |
| 2026-09-26 | Troubleshooting | Run attempt via computer-use hit the known silent-hang gotcha, not a new bug | `swift run PSYBEACON_DISPLAY_COUNT=2` produced only build output, no app logs, no windows — consistent with `AppDelegate.swift`'s documented note that `NSApplication` needs a real interactive WindowServer session; an automation context never fires `applicationDidFinishLaunching` at all. Runtime behavior of the sidecar/multi-display code is still unverified; needs a real Terminal window on the Mac, not a computer-use/agent shell. |
| 2026-09-26 | Handover | Elevated Windows host restarted successfully | `cargo run` from an elevated PowerShell launched `psybeacon-host` successfully and logged `Listening for discovery broadcasts on UDP :43701`. PowerShell note: from `windows-host`, use `cargo run` directly; `&&` is not supported by the user's PowerShell version. |
| 2026-09-26 | Troubleshooting | Multi-display request reaches host but returns no manifest | Mac client successfully routed via Tailscale to `100.90.129.7:43701` and sent `PSYBEACON_START_STREAM_V1` for 2 displays, but received `noReply`. The Windows host logs show `DISPLAY23` and `DISPLAY24` active, followed immediately by Desktop Duplication `access to the display was lost` warnings for both. This places the current failure after display creation, during capture initialization; the host never reaches the manifest reply. |
| 2026-09-26 | Handover | Remote-control environment is a capture variable | The Windows machine is being controlled remotely from a PC while the MacBook runs the client. RDP/Chrome Remote Desktop/other remote-control software may create or alter the active Windows display session and trigger Desktop Duplication `ACCESS_LOST` during virtual-display topology changes. Keep the Windows session unlocked and avoid resolution/session changes; retry with `PSYBEACON_DISPLAY_COUNT=1` first, ideally from the physical console or a remote tool that preserves the active desktop. |
| 2026-09-26 | Troubleshooting | Cleaned up 4 orphaned virtual displays | Failed multi-display test run left 4 stale VDD outputs (1920×1080 each) registered with the driver, visible both via `--diagnose-capture` and the official ParsecVDisplay panel. Confirmed no host process was running (so nothing live was using them), swept `--remove-index 0..7` (safe no-op on empty slots) to remove all without guessing which index mapped to which — unlike the earlier incident, this was fully intentional cleanup, not a wrong guess. One display re-appeared after refreshing the ParsecVDisplay panel: the one backing the user's actual live remote session, which the sweep correctly couldn't tear out from under it. |
| 2026-09-26 | Update | **Milestone: project status check** | Modules 1–3 (discovery, VDD control, capture/streaming) are complete and verified. Module 4's core render path is complete and verified end-to-end over Tailscale. Sidecar input and multi-display orchestration are fully written and compiling clean on both sides, but not yet proven at runtime (blocked on a clean VM test — see the `ACCESS_LOST`-during-multi-display troubleshooting entry above). Clipboard sync and stream-stop-on-disconnect are not started. Rough estimate: **~90% built, ~75% verified** against the original four-module spec. Testing moves to a dedicated VM from this point. |
